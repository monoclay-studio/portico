### (5) Should mutation-proving become the standard for "fails without the fix"?

**Yes, for P0/P1 fixes and for any fix with more than one guard element.** A pre-fix-commit run stays acceptable for a
single-guard P2/P3 fix. Builder v5 BS5-7.

Evidence from a canary I ran this round (`r3-l1`, CPU and local Postgres, ≈ 4 minutes):
- I removed 6 guard elements of the integration-step fix round 2, one at a time, at `db6ae8c`. The builder had
  "proven" those tests by a pre-fix-commit run.
- **5 of 6 mutants were killed.** The survivor is the per-reference **collection lock**: removing it leaves 137/137
  payments tests green. On the fix-round-3 head (`7b0c59c`) it still leaves 142/142 payments and 129/129 API tests
  green (E-114).
- Why: the test "ten concurrent desk deposit charges against a fresh link race" commits the link **before** the
  charges, so nothing races the lock. The builder's report had flagged that this test "already passed before the
  fix"; the pre-fix method surfaced the signal, and nothing required acting on it.
- The guests fix is the counter-example: 14 mutants, each naming the test it turned red, and the two inverse tests
  honestly labelled as passing on old code.

**Limits.** Mutation proves that the guards present are tested; it cannot find a guard that is missing. R3-P1-1 and
R3-P1-2 were missing guards. So mutation pairs with v5's wider closure; it does not replace it. Cost is small: one
payments run takes about 10 seconds, the API suite about 70 seconds.
