# Owner decisions

Decisions made by the owner (Monoclay) that refine the brief. Engineering decisions live in `docs/adr/`.

| # | Date | Decision | Notes |
|---|------|----------|-------|
| D1 | 2026-11-07 | **Product name: Portico** (final — owner confirmed 2026-11-07). Company: **Monoclay LLC** (Delaware, formed via Stripe Atlas; founder based in the Maldives; may run several software products). | Product-level bookkeeping must stay identifiable within Monoclay (product code `portico`). |
| D2 | 2026-11-07 | **Guest payments: the hotel (its legal entity) is the merchant of record.** Preferred embedded option: **Stripe Connect** with Monoclay as platform (may take a platform fee). The payment domain is **provider-agnostic** (Stripe, Adyen, local acquirers, bring-your-own). | Research (doc 04): use *direct charges* so disputes debit the hotel's balance. **Caveat (Q2):** Stripe availability for a Maldivian legal entity is unverified and believed unavailable — Maldives hotels may need a local acquirer adapter. Monoclay's US Stripe account does not make it eligible to collect money for hotels. |
| D3 | 2026-11-07 | **First market: Maldives / Indian Ocean.** | TGST 17%, Green Tax ($12 / $6 per person-night by property class), 10% service charge custom, USD/MVR. |
| D4 | 2026-11-07 | **All segments from day one**: guesthouses, boutique and full-service hotels, resorts, serviced apartments, multi-property groups. The product scales down and up. | Requires plan-based packaging (editions + entitlements) because small and large customers will be priced differently. |
| D5 | 2026-11-07 | **Stack: engineering's choice**, optimizing for time-to-market, very high security, easy migration from incumbent systems, and easy integration with any platform (POS, CRM such as Salesforce, payments, cloud, future APIs). | See ADR-0001..0010. |
| D6 | 2026-11-07 | **Cloud: AWS.** Infrastructure as code (Terraform). | Region choice: OPEN_QUESTIONS Q4. |
| D7 | 2026-11-07 | **OTA connectivity: connectivity hub first** (white-label channel API such as Channex), with our own channel-manager core and an OTA simulator. Direct certifications later. | Google free booking links direct (research doc 04). |
| D9 | 2026-11-07 | **Companion operational-readiness brief adopted** (`docs/product/operational-readiness-brief.md`) as recommendations applied with judgment: 9-level readiness scale with technical vs external-approval tracks, external dependency register, zero-cost demo mode, launch gates, cost model. | Deliverables in `docs/readiness/`. |
| D10 | 2026-11-07 | **Monoclay LLC operates Portico.** Monoclay's existing Stripe account is used for **Portico's own SaaS billing** (Monoclay charging hotels for software, tagged with product code `portico`) and, where eligible, as the **Stripe Connect platform** for hotels whose legal entities are in Stripe-supported countries (direct charges; hotel = merchant). | Verified 2026-11-07 on stripe.com/global and docs.stripe.com: the Maldives is **not** a Stripe-supported country; cross-border payouts only between US/UK/EEA/CA/CH; recipient-agreement accounts cannot process payments. So Monoclay's Stripe cannot be the merchant for Maldivian hotels' guest payments (it would make Monoclay the merchant of record and a payment intermediary — readiness brief §1, §7). Maldives hotels: own bank terminal/gateway recorded in Portico (Route D) and local gateway adapters. |
| D11 | 2026-11-07 | **Plan prices are not set yet.** They will be set after seeing Monoclay's actual costs per property (infrastructure, connectivity, AI, support) and other factors. | Engineering keeps prices as configuration; cost model in `docs/readiness/cost-model.md`. |
| D12 | 2026-11-07 | **Scope: the whole hotel.** Portico covers the entire guest journey (discover → book → pre-arrival → arrival incl. **keys** → in-stay → departure → post-stay follow-up) **and** back-of-house: full accounting (AP, bank reconciliation, assets, budgets, financial statements, tax returns), F&B point of sale & kitchen, procurement, stock & costing, workforce (payroll computation remains a boundary unless decided otherwise), concessions and utilities. | Built as deep, staged modules — not shallow add-ons (brief §12) — and still interoperable with systems a hotel keeps (adoption brief). Audits: `docs/journey/`, `docs/backofhouse/`. |
| D13 | 2026-11-07 | **One-button migration** from any legacy or modern OPERA platform (Fidelio / OPERA 5.x on-premises, OPERA Cloud) and other PMSs: the hotel presses one button and Portico does the rest — discovery, extraction, mapping, validation, rehearsal, reconciliation, delta sync and cutover. | Engineering interpretation that keeps the briefs' honesty rules: *one action for the hotel*; everything automatable is automated; only steps that are legally or technically unavoidable (hotel authorizes data access, vendor-side access approval, sign-off on reconciliation results, non-portable card tokens) remain, shown as a short guided checklist — never hidden, never faked. Research: `docs/research/05-market-deep-dive/11-one-button-migration.md`; build: integration wave 2 migration toolkit. |
| D8 | 2026-11-07 | **No pilot property yet.** Build with realistic Maldives sample data: a guesthouse, a ~120-villa resort, and a 3-property group. All migration importers are planned; generic CSV + OPERA formats first. | |
