# Parity: reservations (incl. front desk)

Status: **v2 · 2026-11-07 · evidence re-run** (parity-researcher playbook v2, PR2-1 and PR2-2; escape E-060) ·
Cluster `front` · Spec `docs/specs/reservations.md` (RES) · Code on `main` @ `2b1d1a6`: `modules/reservations`
(merged).

**What `main` binds.** In `apps/api/src/composition.ts` on `main`, reservations has the real platform and the real
inventory; rates, guests, finance, payments and operations are stubs that answer 503 `module_not_available`
(quotes: `apps/api/test/reservations.test.ts:79-83`), and keys go through the environment fallback adapter. So the
running API on `main` cannot yet create a booking. Every row below is proven at **module level**
(`modules/reservations/test`), where those ports are bound to fakes; S01 and S03 also run against the real inventory
module. The integration step that binds every port is the unmerged branch `feat/integration-step` @ `db6ae8c`.

**v2 evidence re-run.** v1 was written before `modules/reservations` merged, so every row stopped at `specified`. This
pass read the module README (Checkpoint, capability table, Known gaps, "Next (integration)") and every test on `main`,
and set each row to what a test on `main` **asserts**:

- `tested`: a test on `main` asserts every part of the row, **and** the asserted outcome is decided by reservations'
  own code or by a real provider (platform; inventory where the test runs `describe.each(['fake', 'real'])`). A fake
  may supply an input (a price to display, a payment status to read), never the outcome the row claims. The Test
  column quotes the asserting line(s) as `file:line`.
- `built`: the code for the whole row is on `main`, but some part has no asserting test, **or** the claimed outcome is
  decided by a module that is a fake on `main` (rates computes prices, taxes and penalties; finance opens folios and
  routes charges; payments authorizes; operations reports unit condition; guests resolves and merges profiles;
  access encodes keys) — pattern AP-51. The Test column names what is missing (**Not asserted:** …).
- `building`: part of the row is built; another part is not built yet (**Not built:** …).
- A row proven with real bindings only on the integration step is capped at `built`; its Test column says
  `built (feat/integration-step@db6ae8c): <file:line>`.
- Paths `test/…` and `src/…` are relative to `modules/reservations/`; other paths are repo-relative. Line numbers are
  on `main` @ `2b1d1a6`; branch line numbers are on `db6ae8c`.

Edge cases EC-RES-053 … EC-RES-080 come from the failure-class sweep (`docs/quality/patterns.md` groups A–D); the
class is in brackets in the Situation. The sweep record, the classes marked N/A, and the list of rows the README
calls built but this pass did not mark `tested` are in `gaps-front.md` § "v2 evidence re-run".

**Baseline.** OPERA Cloud 26.3 user guide (`ocsuh`): *Bookings → Reservations* (Look to Book, Managing
Reservations with ~60 sub-functions, Reservations Workspace, Room Diary), *Front Desk* (Arrivals and Check In,
In House, Departures and Checkout, Front Desk Workspace, upgrade offers), *Miscellaneous* (Log It, Track It,
service requests, changes log, keys) and *Booking Administration* (alerts, reservation management codes,
waitlist, booking rules). Modern rows from the Mews Connector API and help centre, the Apaleo booking API,
Cloudbeds, Stayntouch and SiteMinder semantics (research 03). Links opened (or found by web search where the
vendor blocks direct fetch) on 2026-11-07. Capability column uses Portico terms (booking, stay, stay segment,
occupant, guarantee, agreed terms, change preview, Timeline, handover, relocation).
