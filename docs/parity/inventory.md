Cluster `front` · Spec `docs/specs/inventory.md` (INV) · Code on `main` @ `2b1d1a6`: `modules/inventory` (merged, bound in
`apps/api/src/composition.ts`).

**v2 evidence re-run.** v1 was written before `modules/inventory` merged, so every row stopped at `specified`. This
pass read the module README (capabilities, invariants, Known gaps, "Competitive parity status") and every test on
`main`, and set each row to what a test on `main` **asserts**:

- `tested`: a test on `main` asserts every part of the row. The Test column quotes the asserting line(s) as
  `file:line` with what each proves. Concurrency rows cite tests that prove the second transaction waited on the
  first one's lock (`pg_stat_activity`) or that race N transactions.
- `built`: the code for the whole row is on `main`, but some part has no asserting test; the Test column names it
  (**Not asserted:** …).
- `building`: part of the row is built (often tested); another part is not built yet (**Not built:** …).
- A row proven only on the unmerged integration step is capped at `built`, and its Test column says
  `built (feat/integration-step@db6ae8c): <file:line>`.
- Paths `test/…` and `src/…` are relative to `modules/inventory/`; other paths are repo-relative. Line numbers are on
  `main` @ `2b1d1a6`; branch line numbers are on `db6ae8c`.
- `assertLedgerConsistent` (INV-I02) runs in the `afterAll` of every integration test file, so each `tested` row
  also ends with a consistent ledger.

The README's own "Competitive parity status" list was **not** copied: rows were checked one by one, and 13 rows it
calls tested stay `built`/`building` because a named part has no asserting line or is not built (list in `gaps-front.md` § "v2 evidence re-run").
Edge cases EC-INV-035 … EC-INV-055 come from the failure-class sweep (`docs/quality/patterns.md` groups A–D); the
class is in brackets in the Situation. The sweep record, including the classes marked N/A, is in `gaps-front.md` § "v2 evidence re-run".

**Baseline.** OPERA Cloud 26.3 user guide (`ocsuh`): *Inventory* chapter (Property Availability, Sell Limits,
Sellable Availability, Room Management, Item Inventory, Alternate Property Availability) and *Inventory
Administration* (rooms inventory, room classes/types, features, pools, unit statuses, overbooking protection,
room rotation). Modern rows from the Mews Connector API, the Apaleo inventory/availability APIs, Cloudbeds,
Stayntouch and RMS (via `docs/research/03`). Evidence links were opened (or, where the vendor site blocks direct
fetch, found through web search) on 2026-11-07. Competitor terms appear in link text; the Capability column uses
Portico glossary terms (unit, unit type, hold, assignment, unit block, authorized overbooking, inventory conflict).

**Status rules for the other values.** `specified` = the INV spec states the behavior and `main` has no code for it
(requirement or invariant cited); `missing` = in no spec and not built; `deferred` = the spec marks it LATER;
`different` = Portico deliberately models it another way (reason in the Spec column).
