## Focus-area summary

- **(a) Money-safety.** Authorization ≠ payment holds (no posting for holds; tested). Refunds with different keys under real concurrency cannot exceed collected (E1; FOR UPDATE + DB check). Broken by P1-4 (adjustments) and races P1-1/P1-2/P1-3. Pending verification is resolved only by lookup/webhook, never by re-send (verified in code: `claim` commits `pending→sent` before the call, `verifyOperation` only looks up, 409/5xx/timeout → unknown); P2-4 makes the "not found" conclusion fragile. At-most-once sending holds (racing executors test is genuinely concurrent).
- **(b) PCI.** No column can hold a PAN by design; tokens are excluded from audit; logs don't print tokens in this module. Gaps: P2-6 (free-text fields, CSV, DB checks, redaction list).
- **(c) Environment safety.** Demo/trial/training always use the simulator, even with Stripe accounts and keys present (tested, HTTP spy 0 calls); sandbox requires `sk_test_`; live refuses simulator accounts; webhook routing separates live/test/simulator. Gap: P1-11 (mode recorded at intent not enforced at execution).
- **(d) Route D.** Recorded payments are clearly labelled (`recorded_unverified`, provenance `external`, `providerVerified: false`, finance stores `verification`), matched by statement import with owned exceptions. Gaps: verification never reaches finance (P1-6), bank transfer posted before receipt (P1-7), fees (P1-9), duplicates (P1-3), adjustments (P1-4), cash aggregates (P2-12), cross-property posting (P0-1).
- **(e) LedgerPort vs finance (`4b657a5`).** Shapes now align through `financeLedgerForPayments` (compile-checked). Precise mismatches: (1) `recordDeposit` without `propertyId` → first deposit fails at runtime (P1-5); (2) consequently deposit refunds fail; (3) no verification-update path (P1-6); (4) the generic `financeProvider(finance,'payments')` lacks `recordPaymentAdjustment`/`recordDisputeMovement` — bind `financeLedgerForPayments`, not `financeProvider`; (5) no `provider` passed → single `card_clearing` (P2-11); (6) neither side applies adjustments to the refund ceiling (P1-4); (7) no property/entity assertion across the port (P0-1); (8) deposit `postingId` is really finance's `entryId` (stored in `ledger_posting_id`); (9) finance's `PaymentsPort.requestCollection` (late charges) has no payments provider — finance stays on its stub; (10) cash without a cashier session is now posted and flagged by finance (`cashWithoutSession: 'flag'`), which is acceptable but means system-actor retries never attach a session.
