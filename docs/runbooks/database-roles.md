# Runbook: database roles

**Status:** verified on a local SCRAM-auth PostgreSQL 16 with `infra/db/verify-roles.sh` (38 checks: bootstrap,
migrations as a non-superuser owner, routing grants twice, privilege probes, API and worker under their own logins
from the production runtime layout, restore-drill SQL with planted defects). **Not yet run on RDS/Aurora**
(differences: `rds_superuser`, the RDS-managed master secret, IAM authentication).

Related: ADR-0002 (RLS), ADR-0004 (outbox worker), `infra/db/bootstrap-roles.mjs`, `packages/db/src/migrate.ts`.

## The roles

| Role | Login | Used by | Can | Cannot |
|---|---|---|---|---|
| RDS master (`dbmaster`; never a `portico_*` name, which the privilege checks reserve for unprivileged roles) | yes (RDS-managed secret) | `db-bootstrap` task only | create roles, extensions | is never used by the application or migrations |
| `portico_owner` | yes | migration task, `grants` step | own and change every schema, table, function | superuser, CREATEROLE, CREATEDB, BYPASSRLS; it is not used at runtime |
| `portico_app` | **no** (group) | — | the table/function privileges every migration grants; **RLS applies** | log in; execute job-routing functions (revoked) |
| `portico_app_blue` / `portico_app_green` | yes | API tasks (one active, one standby) | everything `portico_app` can; `statement_timeout 60s` | anything else |
| `portico_worker` | **no** (group, member of `portico_app`) | — | everything `portico_app` can **plus** the job-routing `SECURITY DEFINER` functions | bypass RLS; read the non-RLS directory tables |
| `portico_worker_blue` / `portico_worker_green` | yes | worker tasks | as `portico_worker`; `statement_timeout 300s` | — |
| `portico_ops_readonly` | IAM auth only (resilient) | humans, audited read-only investigation | read, with `default_transaction_read_only` | write; RLS still applies |

Why a separate worker role: the routing functions (`payments.tenants_for_jobs`, `integration.claim_due_tenants`,
`inventory.tenants_with_*`, `operations.job_properties`, `guests.tenants_with_*`, `reservations.due_booking_expiries`,
`core.claim_*` …) return cross-tenant routing metadata. Request handlers never need them, so the API's role cannot
call them (payments review P3-5). The list lives in `ROUTING_FUNCTIONS` in `bootstrap-roles.mjs`.

**Pending (outside infra):** `payments.route_webhook` (the public Stripe webhook route, before any tenant context)
stays executable by `portico_app` until the API serves that route through a `portico_worker` pool. Then: move it to
`workerOnly`, set the production variable `api_holds_worker_credentials = true` (injects `WORKER_DATABASE_URL` into the
API), and have `packages/db` create `portico_worker` in its development bootstrap so module migrations can grant to it
directly (requests filed in `infra/README.md` § Requests to other modules).

## Two phases, every deploy

| Phase | Command | Runs as | When |
|---|---|---|---|
| roles | `node /app/ops/bootstrap-roles.mjs` | RDS master | first deploy; after every credential rotation (`--bootstrap-roles`) |
| grants | `node /app/ops/bootstrap-roles.mjs grants` | `portico_owner` | after **every** migration run (the pipeline does it) |

Both are idempotent and take an advisory lock. The roles phase ends by refusing to continue if any `portico_*` role is
privileged. The grants phase verifies with the server's own `has_function_privilege` and fails the deploy if the
worker cannot execute a routing function or the app still can; it also warns about any **unreviewed** `SECURITY
DEFINER` function the app can execute — review it (sign-in/tenant lookups → `APP_DEFINER_FUNCTIONS`; job routing →
`ROUTING_FUNCTIONS.workerOnly`) before the next release. `verify.sql` check 7 enforces the same list in the drill.

## Secrets

`<secret_path>/db/owner`, `/db/app`, `/db/worker` (JSON: `username`, `password`, `standby_username`,
`standby_password`, `host`, `port`, `dbname`, `url`). ECS injects `url` as `APP_DATABASE_URL` (api ← app, worker ←
worker) and `DATABASE_URL` (migrate ← owner). Initial values are generated by Terraform through write-only attributes:
**they are not in Terraform state or plans**. Terraform never changes them again.

## Rotation (alternating users — no downtime)

Rotate the **standby** login, then make it active. The running tasks keep the old login, which still works.

```bash
S=portico/production/aps1-c01/db/app        # or …/db/worker
NEW=$(aws secretsmanager get-random-password --password-length 40 --exclude-punctuation --query RandomPassword --output text)
aws secretsmanager get-secret-value --secret-id "$S" --query SecretString --output text \
| NEW="$NEW" jq '
    {u: .username, p: .password} as $old
    | .username = .standby_username | .password = env.NEW
    | .standby_username = $old.u | .standby_password = $old.p
    | .url = "postgres://\(.username):\(.password)@\(.host):\(.port)/\(.dbname)?sslmode=verify-full"' \
| aws secretsmanager put-secret-value --secret-id "$S" --secret-string file:///dev/stdin >/dev/null
unset NEW
```

Then run the deploy workflow with `bootstrap_roles = true` (or run the `db-bootstrap` task alone, then force a new
deployment of the service). Check the API/worker logs for authentication errors; the previous login stays valid until
the next rotation, so rolling back is: swap the fields back and redeploy.

- `portico_owner`: one login. Rotate when no migration runs: new password → `put-secret-value` → `db-bootstrap`.
- RDS master: managed by RDS (`manage_master_user_password`); rotate with the RDS console/API; run `db-bootstrap`
  afterwards only to confirm it still connects.
- Never paste a password into a terminal argument, a ticket or a chat; the snippet keeps it in a variable and stdin.

## Application keys are NOT database credentials

`<secret_path>/app/field-key`, `blind-index-key`, `terms-seal-key` are irreplaceable for the data they protect and
are **not rotated** by any procedure here (key-rotation support with key ids is a kernel follow-up). The
`payments-simulator-signing-secret` may be rotated at will (in-flight simulated webhooks fail verification once).

## Investigating as a human

Resilient tier: connect with IAM authentication as `portico_ops_readonly` (read-only, RLS applies — set
`app.tenant_id` to look at one tenant). Every session is an audit event; record the reason in the incident.
Never use the master or owner credentials for investigation. ECS Exec is off in production
(`enable_execute_command = false`); turning it on is an incident decision.
